# イベナウ（EVENOW）将来構想・長期方針

> **これは将来構想であり、現時点では実装しない。** 今は利用者獲得と基本機能（イベント情報・会場マップ・現地情報の共有）の完成を最優先する。
> 将来この機能を足すときに大きく作り直さずに済むよう、方針として保持する。

## 現在 と 将来 の区別

| | 内容 |
|---|---|
| **現在（実装済み・実装中）** | イベント情報、会場マップ、現地情報の投稿・閲覧、自動収集（設計）、SNS共有・ハッシュタグ |
| **将来（利用者・閲覧数が十分に増えてから）** | ポイント、全国共通ポイント、イベント限定クーポン、スポンサー・協賛、QRでの利用確認 |

## 将来やりたいこと

1. **投稿ポイント**：駐車場の空き・トイレの待ち時間・行列・売り切れ・混雑などの投稿にポイントを付与。
   投稿数ではなく、新しさ・役立ち度（他の人の閲覧・確認）を重視し、重複・不正は付与しない。
2. **全国共通ポイント**：どのイベントで貯めたポイントも、別のイベントで使える。**現金化はしない。** 価値を無制限に保証しない。
3. **イベント限定・枚数限定クーポン**：ポイントの交換先。例「たこ焼き100円引き・先着100名」。
   発行枚数・期限・利用店舗・条件を必ず設定し、上限に達したら自動で配布終了。どのイベントでも使えるクーポンは作らない。
4. **スポンサー収益**：スポンサー掲載料、イベント単位の協賛金、メインスポンサー枠、クーポン掲載・キャンペーン費用、
   ポイントキャンペーン費用、利用実績に応じた成果報酬、将来の広告。スポンサーには取得数・利用数・参加者数をレポート。
5. **クーポン利用**：スマホでクーポンのQRを表示 → 出店者がブラウザで読み取り → 利用済みに記録（二重利用防止）。出店者に専用アプリは入れさせない。

## 必ず守るルール（イベナウは自腹を切らない）

1. 協賛金の入金・予算確保の前にクーポンを発行しない
2. クーポンの割引原資をイベナウが立て替えない
3. 発行枚数には必ず上限を設定する
4. 確保済み予算を超えるクーポンを発行しない（予算と発行上限を連動）
5. 協賛企業がいないイベントでは、クーポンを無理に提供しない
6. 配布数・利用数・残数はシステムで自動管理する
7. イベナウが店舗との個別精算・立替をしない仕組みにする

イベナウは資金負担者ではなく、スポンサー・参加者・出店者をつなぐプラットフォーム。

## 一人で運営できることを最優先

発行・終了・残数管理、ポイント付与・交換履歴、QR利用確認、スポンサー別集計、予算と上限の連動、
不正投稿・不正取得・二重利用の防止をすべて自動化し、問い合わせ・個別対応・手作業の精算が増える仕組みは避ける。

## 今の設計で気をつけておくこと（過剰な先行開発はしない）

- 投稿（reports）にはブラウザ単位の匿名ID（client_id）を記録済み → 将来、投稿とポイントを結び付けられる。
  ポイントを導入するときは、ログイン（ユーザーアカウント）を任意で追加する（今は不要）。
- 投稿の通報・非表示・連投制限はすでにあり、不正対策の土台になる。
- ポイント・クーポン・スポンサーのテーブルは、**実装すると決めた時点で追加する**（今は作らない）。
