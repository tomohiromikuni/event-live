# 自動収集・ページ生成・SNS自動投稿 設計提案

> **第1段階は実装済み（2026-11-25）**：情報源の登録（`/admin/sources`）→ 毎日の収集（`/api/cron/collect`・GitHub Actions）→
> AIで整理（`lib/collect/extract.ts`）→ 重複チェック（`lib/collect/dedupe.ts`）→ 候補の確認（`/admin/candidates`）→ 承認で非公開イベントを作成。
> 実行状況は `/admin/collect`。必要な設定は README の「自動収集の設定」。

作成: 2026-11-24 ／ 対象: EVENOW（Next.js on Vercel + Neon PostgreSQL）

## 0. 前提と方針

- **既存の仕組みを最大限再利用する**
  - 収集した情報は「下書き形式」（`docs/DRAFT_FORMAT.md`）に変換し、既存の取り込み処理（`app/admin/import-actions.ts`）で登録する。
  - 会場マップは「マイマップ取り込み」（`lib/kml.ts`）や「ガイドマップから作図」を使う。
  - ページは既存の共通テンプレート（`/events/[slug]`）で自動的に生成される（イベント別のサイトは作らない）。
- **掲載基準は維持する**：会場マップ（施設3件以上、うちトイレか駐車場1件以上）があるイベントだけを公開する。
  自動収集したイベントは、まず **非公開の「候補」** として登録する。マップのある候補だけを公開・SNS発信の対象にする。
- **誤情報を大量に公開しない**：AIが抽出した情報は推測で埋めず「未確認」とし、信頼度の低いものは人の確認を必須にする。

## 1. 全体の流れ

```
[毎日 定期実行]
  ① 収集  : 登録済みの情報源（オープンデータ / RSS / 公式サイト / マイマップ）を巡回
            ↓ 前回から内容が変わったものだけ（ハッシュ比較）
  ② 抽出  : Claude API（Message Batches・50%割引）で下書き形式のJSONに整理
            ↓
  ③ 照合  : 既存イベント・既存候補と重複チェック（名前の正規化＋開催日＋都道府県＋類似度）
            ↓ 新規 → 候補 ／ 既存 → 変更点（日程変更・中止など）を記録
  ④ 判定  : 信頼度スコアを計算。高い＋マップあり → 自動公開（設定でON/OFF）／それ以外 → 確認待ち
            ↓
  ⑤ 公開  : 共通テンプレートでページが自動生成（SEOタイトル・説明文・構造化データは既存の仕組み）
            ↓
  ⑥ 発信  : 投稿キューに積む（新規・明日開催・本日開催・週末まとめ）→ 設定した時間帯・上限内でSNSへ投稿
            ↓
  ⑦ 後処理: 終了したイベントは自動で「終了」表示。中止・延期の変更は確認待ちに回す
```

## 2. 情報源（収集する方法）

| 優先 | 情報源 | 取得方法 | 補足 |
|---|---|---|---|
| ◎ | **自治体標準オープンデータセット「イベント一覧」**（デジタル庁が形式を定めたCSV） | CSVをそのまま取り込み | 形式が決まっていてAI不要。利用条件（CC BY等）を確認して登録 |
| ◎ | **Google マイマップ**（公式が公開しているもの） | KML（実装済み） | 会場マップの元データ。公式サイトにリンクがあれば自動で見つける |
| ○ | **観光協会・自治体サイトの RSS**（WordPress なら `/feed/`） | RSS | 新着の検知に使い、本文はAIで抽出 |
| ○ | **イベント公式サイト** | HTML取得 → 本文抽出 → AI | 利用規約・robots.txt を確認して「許可した情報源」にだけ登録 |
| △ | 管理者がURLを貼る | 同上 | 収集の網から漏れた大型イベント用（いつでも使える手動ルート） |

- 情報源は管理画面で登録し、**利用規約の確認日・robots.txt の可否**を記録する。未確認の情報源は巡回しない。
- アクセスは1サイトにつき1日1回程度。ページ間に間隔をあける。User-Agent にサービス名と連絡先URLを入れる。
- 写真・紹介文・ガイドマップの画像は転載しない（事実のみ抽出し、概要は要約）。

## 3. AIによる情報整理（Claude API）

- **出力形式**：構造化出力（`output_config.format` に JSON Schema）で、下書き形式の `event` 部分を返させる。
  各項目に「ページ上の根拠となる文」も返させ、根拠がない項目は空＝「未確認」にする。
- **モデル**：既定は `claude-haiku-5-5`（費用優先・運営者の判断）。精度が足りないときだけ環境変数 `COLLECT_MODEL=claude-opus-5-5` に切り替える。
- **費用を抑える工夫**
  1. 変化したページだけ処理（ハッシュ比較）、イベントらしくないページは事前に除外（日付・会場などのキーワード判定）
  2. HTMLから本文だけを抜き出してトークンを減らす（メニュー・広告・スクリプト除去）
  3. **Message Batches API**（非同期・料金50%）。毎日の収集は急がないので最適
  4. 共通の指示文（システムプロンプト）に**プロンプトキャッシュ**を使う
  5. オープンデータ（CSV）は AI を使わずに取り込む
- **概算**（1ページ＝本文4,000トークン前後の場合。2026-11 時点の公開価格。実測で要調整）

  | モデル | 料金（入力/出力 1Mトークン） | 1ページあたり（Batches利用） |
  |---|---|---|
  | Claude Opus 5.5 | $4 / $20 | 約 $0.015〜0.03（2〜4円） |
  | Claude Haiku 5.5 | $0.10 / $0.50 | 約 $0.0005 未満（0.1円未満） |

## 4. 重複検出と信頼度

- **重複**：イベント名を正規化（全角半角・空白・「第○回」・年号を除去）＋都道府県＋開催日の重なり → 一致なら同一。
  近いもの（名前の類似度が高い・日程が重なる）は「重複の疑い」として確認待ちにする（PostgreSQL の pg_trgm を使用）。
- **毎年開催のイベント**は「シリーズ」として同じURL（例: `/events/omagari-hanabi`）を使い続け、年ごとの日程を更新する（検索評価が年々たまる）。
- **信頼度スコア**（0〜100）：情報源の種類（公式・自治体＞観光協会＞その他）、必須項目の充足、根拠文の有無、複数の情報源での一致。
  - 80以上＋マップあり → 自動公開（設定でON/OFF。最初はOFFを推奨）
  - それ以外 → 管理画面「確認が必要なイベント」へ

## 5. ページの自動生成・終了処理

- ページは既存テンプレートで自動生成済み（SEOのタイトル・説明文・構造化データ・サイトマップも自動）。
- 追加するもの：
  - 「最終確認日時」「情報源」の表示（既存の source_url / source_checked_at を自動更新）
  - 終了したイベントは「このイベントは終了しました（次回の情報は確認中）」と表示し、ページは残す（翌年の検索に効く）
  - 中止・延期の変化を検知したら確認待ちにし、確認後に反映する

## 6. SNS 自動投稿

- **構成**：投稿先ごとに「アダプター」を用意する共通の仕組み（`post(text, url, image?)` を実装するだけで SNS を追加できる）。
  最初は X、次に費用のかからない Bluesky / Threads を追加する想定。
- **投稿文**：**基本はテンプレートで作る**（日付・場所・URLを確実に正しく入れるため。費用もかからない）。
  AIは「今週末まとめ」の見出しなど、言い回しを整える部分だけに任意で使う。
- **投稿の種類**：新規掲載／明日開催／本日開催（現地の状況の案内）／今週末まとめ／注目イベント
- **管理画面**：ON/OFF、SNSの選択、時間帯、1日の上限、対象ジャンル・地域、投稿文の編集、予約、履歴、エラー一覧
- **X API の費用（要確認）**：2026年は従量課金が基本で、**URL付きの投稿は1件あたり約$0.20**とされている（URLなしは約$0.015）。
  1日3件で月約$18（約2,700円）。公式の料金ページ（docs.x.com）で最新の単価を確認してから有効にする。
  → 上限（1日の件数・月の予算）を設定できるようにし、超えたら止める。

## 7. 定期実行

- **GitHub Actions のスケジュール実行**から EVENOW の専用API（`/api/cron/*`、秘密のトークンで保護）を呼ぶ。
  公開リポジトリなら無料で、実行間隔も自由（Vercel の無料プランの Cron は回数に制限がある）。
- 処理は小分けにする（1回の呼び出しで処理する件数を絞り、残りは次回へ）。Vercel の実行時間制限に収めるため。
- 失敗したものは次回に自動で再実行（回数上限つき）。実行結果は「実行履歴」に保存し、管理画面に表示。

## 8. データベースに追加する表

| 表 | 内容 |
|---|---|
| sources | 情報源（種類・URL・地域・有効/無効・規約確認日・最終取得日時・前回の内容ハッシュ） |
| crawl_runs | 実行履歴（開始/終了・取得数・新規数・重複数・エラー数・ログ） |
| event_candidates | 候補（情報源・抽出結果＝下書き形式・根拠・信頼度・状態［確認待ち/承認/却下/統合］・対応イベント） |
| events（列追加） | series_key（毎年同じURL用）、confidence、last_checked_at |
| sns_settings / sns_posts | 投稿設定、投稿キュー兼履歴（種類・本文・予約時刻・状態・エラー・SNS側のID） |

## 10. 段階的な進め方

- **第1段階（小規模で一通り動かす）**：情報源の登録 → 毎日の収集 → AI抽出 → 重複チェック → 候補の確認画面 → 承認で非公開イベント作成 → 終了処理 → X投稿（テンプレート・手動承認つき）
- **第2段階**：オープンデータの取り込み、マイマップの自動発見、信頼度による自動公開、Bluesky / Threads 対応、投稿の自動化
- **第3段階**：対応地域・情報源の拡大、時間帯ごとの混雑傾向の自動まとめ（検索・SNS用）
